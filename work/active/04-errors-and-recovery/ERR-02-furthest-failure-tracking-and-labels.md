# ERR-02: Furthest-failure tracking and labels

## Summary

Report the furthest failure with merged expectations, without allocating until a failure is actually reported.

## Scope

- Per-layer furthest failure stored as a buffer index plus an interned expectation-set handle.
- Merge failures at equal positions as [ADR-0021](../../docs/decisions/0021-how-failures-are-recorded-and-merged.md) point 1 says: expectations in recording order without duplicates, the first message, the first failure's context stack, and the longest behind-the-cursor span. Build `ParseError` lazily.
- `Named` replaces the expectations `p` recorded at its start position whenever `p` consumes nothing, on failure or success, and adds none if there were none ([ADR-0008](../../docs/decisions/0008-control-node-semantics.md) point 4). Expectations recorded there before `p` ran stay, a failure with no expectations counts, and a message is never removed ([ADR-0021](../../docs/decisions/0021-how-failures-are-recorded-and-merged.md) point 3).
- What each primitive records ([ADR-0021](../../docs/decisions/0021-how-failures-are-recorded-and-merged.md) point 6). A failed `Custom` records its `Name` as a `Label`, or else its `First` as one expectation ([ADR-0012](../../docs/decisions/0012-custom-scanner-metadata.md) point 4, as ADR-0021 refines it). `Satisfy`, `Any` and a `Custom` with neither record a failure with no expectation.
- `Lookahead` and `Not` restore the furthest failure, and a `Not` whose parser succeeds records a failure with no expectations at its start (ADR-0021 point 2).
- Dispatch records what the alternatives it skips would have expected, precomputed in lowering for each gap between candidates (ADR-0021 point 5; [ADR-0016](../../docs/decisions/0016-or-dispatches-on-each-alternatives-leading-item.md) point 4).
- A rejected filter ([ADR-0014](../../docs/decisions/0014-a-rejected-filter-reports-at-the-start-of-the-value.md) points 2 to 6). It is reported at the start of the rejected value, with a span over that value. When the predicate rejects, the furthest failure is restored to what it was before the filter's parser ran, and then the rejection is recorded. `Where(predicate, message)` records what `Fail(message)` records. Without a message, the rejected input is unexpected. A rejection counts as a failure at its start for `Named`. It lies behind the cursor, so what its error needs is captured by value, without allocating or pinning. The non-associative chain error ([ADR-0004](../../docs/decisions/0004-expression-build-operator-table-and-semantics.md) point 4), reported at a consumed operator's span, follows the same capture rule. INT-04 runs both and leaves their recording here (ADR-0014 point 7).
- Compiled subtrees ([ADR-0017](../../docs/decisions/0017-regular-subtrees-compile-to-an-eager-commit-aware-automaton.md) point 6, settled by [ADR-0022](../../docs/decisions/0022-a-successful-longest-restores-the-furthest-failure.md)). A successful `Longest` restores the furthest failure, in `LongestPlan` and the compiled plan alike. So `DfaLongestPlan` records nothing on a match, and a non-match re-runs on the interpreter as now. No scan extent is exposed.
- `Context` stack (ADR-0021 point 4). A line applies only to failures past its construct's start, and records its first item's position, mapped to a span when the error is built. Capturing spans by value for streamed input is [LAY-01](../06-layers-and-pipelines/LAY-01-streambuffer-and-pulling-cursor.md)'s. `ParseError.Context` becomes `IReadOnlyList<ContextLine>`, with `ContextLine(string Text, SourceSpan Start)`. That changes ERR-01's `ParseError`, its tests and docs/concepts/errors.md, and ERR-03's renderer and snapshots, which print "starting at 2:1" from `Start`. Both cards are Done; the changes are made here.
- Settled by ADR-0021, raised by the CORE-08 review: inner failures of `Not` and a successful `Lookahead`, what `Not` records when its parser succeeds, the context stack of a merged failure, `Named` and earlier expectations, and what skipped dispatch attempts contribute.
- Display ([ADR-0023](../../docs/decisions/0023-token-types-describe-their-kinds.md)). `IKinded<TKind>` gains `static virtual string Describe(TKind kind) => kind.ToString()` and `string? Detail => null`, called only when an error is built. Engines reach them through a token grammar, so a token type shows through them once a `TokenGrammar<TToken, TKind>` over it is initialised (ADR-0023 point 3). Expected kinds show `Describe(k)`. An unexpected token shows `Describe(kind)`, then its `Detail` when present. A null or empty `Describe` falls back to `kind.ToString()`. Characters, strings, `Token(x)` items and `Case<TCase>()` (its type name) display as ADR-0023 point 5 says. `Creole.AotSmoke` gains a token that overrides both members, and the tests include a union token that does. docs/ shows the explicit implementation syntax.

## Acceptance criteria

- [x] The whitepaper's rendered JSON error is reproduced exactly.
- [x] Failure paths allocate nothing in benchmarks.
- [x] A rejected filter and a chained non-associative operator are reported as ADR-0014 and ADR-0004 point 4 say, and building their errors reads no buffer item behind the cursor.
- [x] Every point of ADR-0021 has a test. Dispatch records the same failure as running in order: INT-05's dispatch exactness tests compare recorded failures, and the CORE-08 control table gains expected sets.
- [x] A compiled and an interpreted `Longest` leave the same furthest failure, for matches and non-matches, over `RegularShapes` and the lexer samples (ADR-0022).

## Outcome

Delivered furthest-failure reporting for the interpreter, under [ADR-0021](../../docs/decisions/0021-how-failures-are-recorded-and-merged.md), [ADR-0022](../../docs/decisions/0022-a-successful-longest-restores-the-furthest-failure.md) and [ADR-0023](../../docs/decisions/0023-token-types-describe-their-kinds.md). Each layer keeps one failure record in a reusable `FailureLog<T>`. Primitives, control nodes, dispatch, filters and chained operators record into it, and it builds the one reported `ParseError` when asked. Recording allocates nothing; building the error allocates only the error.

Deviations and decisions:

- [ADR-0021](../../docs/decisions/0021-how-failures-are-recorded-and-merged.md), [ADR-0022](../../docs/decisions/0022-a-successful-longest-restores-the-furthest-failure.md) and [ADR-0023](../../docs/decisions/0023-token-types-describe-their-kinds.md) (Accepted) settled the card's open choices. ADR-0021 point 4 and ADR-0023 point 3 were edited in place before merge, as their "Changes made" say. A `Context` records its start position, which in-memory input maps to a span exactly, and LAY-01 captures spans by value. A token type shows through `Describe` once a token grammar over it is initialised.
- The time cost of recording is the open risk for [BENCH-01](../13-benchmarks/BENCH-01-phase-0-speed-gate.md). On token JSON (default job), recording costs 1.46x (`Plain` 83.2 µs, `PlainRecording` 121.7 µs) and 1.50x on the invalid copy. `Named` and `Context` cost 1.16x with no log. Cheaper recording that keeps behaviour (a fast path with no log, deduplicating gaps at lowering) is not a card yet; propose one if BENCH-01 needs it.
